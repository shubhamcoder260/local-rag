# Project Overview

## What this is

**local-rag** is a fully local, self-hosted Retrieval-Augmented Generation
(RAG) system. You upload documents (PDF or plain text), ask questions about
them in natural language, and get answers grounded in the actual content of
those documents — generated by a locally-running LLM, with no cloud service,
no API key, and no data ever leaving the machine it runs on.

At its core, it does four things:

1. **Ingest** — take a document, break it into overlapping text chunks,
   convert each chunk into a vector embedding, and store those embeddings in
   a local vector database.
2. **Retrieve** — take a question, embed it the same way, and find the
   stored chunks whose embeddings are closest to it (i.e. most likely to be
   relevant).
3. **Generate** — hand those retrieved chunks to a local LLM as context, and
   stream back an answer that's grounded in them rather than the model's own
   (unverifiable, un-sourced) general knowledge.
4. **Serve** — expose all of this through a small web UI and a documented
   HTTP API, all running in Docker.

## Why it exists

This project started as a learning-by-building exercise: the goal was never
just to get a RAG demo working, but to actually understand *why* each piece
works the way it does — how chunking strategies affect retrieval quality,
why batching embedding calls matters, why Ollama's networking behaves
differently depending on whether it's containerized, and so on. Almost every
design decision documented in this `docs/` folder came out of hitting a real
bug or a real performance wall first, then fixing it and understanding the
fix, rather than starting from a textbook architecture.

That history matters for how these docs are written: wherever possible, a
decision is described along with *what broke without it*, not just what the
final code does. See `09_CHANGELOG.md` for the full bug-and-fix history, and
`05_DEVELOPMENT_ROADMAP.md` for where things are headed next.

## Core design principles

These hold across every part of the system, and any future change should be
checked against them:

- **Fully local, always.** No cloud LLM calls, no API keys, no telemetry.
  Ollama runs on the host machine; the vector database is an embedded local
  library (ChromaDB in `PersistentClient` mode), not a separate server.
- **No hardcoded chat model.** The embedding model
  (`nomic-embed-text`) is fixed, since ingested data and queries must be
  embedded the same way to be comparable — but the *chat* model is chosen
  freely from whatever is installed on the host via Ollama, discovered
  dynamically through `GET /models`.
- **Per-document isolation.** Each ingested document gets its own vector
  collection rather than sharing one global collection, specifically to
  prevent cross-document contamination when answering a question about one
  specific document.
- **Evidence over assumption.** Performance claims, model recommendations,
  and architectural choices in this project are backed by something that was
  actually measured — see `07_BENCHMARKS.md`. Where a claim (e.g. from an
  external proposal, or a paper) hasn't been tested against this project's
  own hardware and stack, that's called out explicitly rather than adopted
  on faith.

## Current status (high level)

- The full pipeline — ingest (text + PDF) → chunk → embed → store → ask →
  retrieve → generate (streamed) — is implemented and working end-to-end.
- The codebase was recently refactored from a single monolithic `api.py`
  into a proper `ingestion` package with clear separation of concerns
  (chunking, embedding, extraction, storage, and orchestration each in their
  own module). See `02_DIRECTORY_STRUCTURE.md`.
- Two significant early bugs — unbounded/impractical chunking on non-prose
  input, and slow one-chunk-at-a-time embedding — were identified, fixed,
  and verified. See `09_CHANGELOG.md`.
- The project is Dockerized (FastAPI backend + Streamlit frontend as
  separate containers) with Ollama running on the host, and ships with an
  interactive Linux setup script that handles prerequisites and hardware-
  based model recommendations.
- Research into memory- and latency-optimized RAG techniques for
  resource-constrained hardware (the EdgeRAG paper) is underway, aimed at a
  possible future architectural enhancement. See `08_EDGE_RAG_RESEARCH.md`
  and `06_PSIP_DESIGN.md`.
